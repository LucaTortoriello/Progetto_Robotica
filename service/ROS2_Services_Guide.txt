INTRODUZIONE AI SERVICES
================================================================================
I Service sono uno dei meccanismi di comunicazione principali in ROS 2. A 
differenza dei Topic (comunicazione asimmetrica publish/subscribe), i Service 
implementano un modello di comunicazione SINCRONO (Richiesta/Risposta).

Un Service consente a un nodo client di inviare una richiesta a un nodo server 
e aspettare una risposta specifica prima di continuare l'esecuzione.

ARCHITETTURA CLIENT-SERVER
================================================================================

Server
   - Riceve una richiesta da un client
   - Elabora la richiesta
   - Invia una risposta
   - Rimane in attesa di nuove richieste
   - Può servire più client in sequenza

Client
   - Invia una richiesta al server
   - Attende la risposta (blocca l'esecuzione)
   - Riceve i dati di risposta
   - Continua l'esecuzione dopo la risposta
   - Può aspettare con timeout

Definizione Interface
   - Request: struttura dati della richiesta
   - Response: struttura dati della risposta
   - Definite in file .srv (Service Definition)


CREAZIONE DI UN SERVICE (.srv)
================================================================================

Un file .srv definisce la struttura della richiesta e della risposta.
Formato: <nome_package>/srv/<nome_service>.srv

Sintassi:
---
<tipo_dato> <nome_campo>  # Request
---
<tipo_dato> <nome_campo>  # Response
---


COMANDI UTILI DA TERMINALE
================================================================================

# Lista tutti i service disponibili
ros2 service list

# Mostra il tipo di un service
ros2 service type <nome_service>

# Lista tutti i service di un certo tipo
ros2 service type -t <tipo>

# Mostra la definizione di un service (.srv)
ros2 service find <tipo_service>

# Informazioni dettagliate su un service
ros2 interface show <package>/srv/<ServiceName>


Chiamare un Service da Terminale:

# Sintassi generale
ros2 service call <nome_service> <tipo> '{campi}'

# Esempio - Service con numeri
ros2 service call /sum_service my_package/srv/AddTwo '{a: 5, b: 3}'

# Esempio - Service con stringhe
ros2 service call /move_robot my_package/srv/MoveTo '{x: 1.0, y: 2.0, z: 3.0}'

# Esempio - Service con array
ros2 service call /execute_trajectory my_package/srv/Trajectory '{path: [1, 2, 3, 4, 5]}'

# Con formato JSON
ros2 service call /example_service package/srv/Example \
  --print-response \
  '{field1: value1, field2: value2}'


Debugging e Monitoring:

# Monitora tutte le chiamate a un service
ros2 service list --count

# Verifica quali nodi offrono un service
ros2 node list

# Visualizza topic pubblicati dal service
ros2 topic list

# Graphical tool per visualizzare service
rqt_service_caller  # GUI interattiva


CICLO DI VITA DI UNA CHIAMATA A SERVICE
================================================================================

1. SERVER CREATION
   - Server registra il service con il middleware ROS 2
   - Server si mette in attesa di richieste
   - Log: "Service available"

2. CLIENT CREATION
   - Client crea il client object
   - Client cerca il service (wait_for_service)
   - Se servizio trovato, pronto per inviare richieste

3. REQUEST TRANSMISSION
   - Client prepara la richiesta con i dati
   - Invia la richiesta al server via middleware
   - Si blocca aspettando la risposta (o registra callback)

4. SERVER PROCESSING
   - Server riceve la richiesta
   - Callback del server viene eseguito
   - Server elabora i dati
   - Server crea la risposta

5. RESPONSE TRANSMISSION
   - Server invia la risposta al client
   - Middleware consegna la risposta

6. CLIENT RECEIVES
   - Client riceve la risposta
   - Se sincrono: continua l'esecuzione dopo il call()
   - Se asincrono: esegue il response_callback

7. CONNECTION CLEANUP
   - Se non più usato, il client può liberare risorse
   - Se server termina, nuove richieste falliscono

CONSIGLI UTILI
================================================================================

Design di Service:
- Usa service per operazioni DISCRETE (completare/fallire)
- Usa topic per STREAM di dati continui
- Mantieni request/response SEMPLICI ed ESSENZIALI
- Evita service per operazioni che richiedono UPDATE CONTINUI

Implementazione:
- SEMPRE aspetta che il servizio sia disponibile (wait_for_service)
- Implementa TIMEOUT per evitare blocchi indefiniti
- Usa try/except per gestire eccezioni
- Log appropriati per debugging
- Documenta il servizio nella docstring

Performance:
- Service sincroni possono bloccare il nodo
- Usa callback asincroni se possibile
- Evita operazioni lunghe nel callback del server
- Monitora i tempi di risposta

Sicurezza:
- Valida sempre i dati ricevuti nel server
- Implementa controlli dei parametri
- Gestisci eccezioni per evità crash
- Log di tutte le operazioni critiche


RISOLUZIONE PROBLEMI
================================================================================

Problema: "Service not available"
- Verificare che il server sia in esecuzione (ros2 node list)
- Controllare il nome del service (ros2 service list)
- Aumentare il timeout in wait_for_service
- Verificare il namespace del service

Problema: "Timeout nella risposta"
- Il server è troppo lento
- Aumentare il timeout
- Debuggare la logica del server
- Verificare se il server è bloccato

Problema: "Tipi di dato non corrispondono"
- Rigenerare i package Python dopo modifica .srv
- Importare il tipo corretto nel client/server
- Verificare la versione dei package

Problema: "Client non riceve la risposta"
- Verificare che la risposta sia completamente inizializzata
- Controllare che il server ritorna effettivamente la risposta
- Verificare la connettività di rete (per sistemi distribuiti)
